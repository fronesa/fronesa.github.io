API reference — FD-1 Decision API

Decisions, documented from the contract.

The production API lives at https://fronsea-api.onrender.com and runs code v10. The general decision endpoint is POST /decide/v2: send one state text plus up to 16 typed questions — yes/no, multiple choice, scored — and get one calibrated answer per question. The original spam endpoint, POST /decide, remains live and frozen as v1. This page documents the contract the production code actually enforces: schemas, limits, and error codes.

The v2 endpointError reference
1 — Authentication & limits

A key on every call.

Every decision endpoint requires an API key, sent as Authorization: Bearer <key>. A missing or invalid key returns 401. There is no keyless v2 lane — the keyless demo lane exists only on the v1 POST /decide endpoint, only from this site’s pages. To get a key, email surety.ai@proton.me.

LimitValue
Rate limit100 requests/minute per key, one shared budget across the decision endpoints. On /decide/v2, each question consumes one unit; a batch of N texts on /decide/batch consumes N. Over the limit: 429 with a Retry-After header.
Request body — POST /decide/v2128 KB maximum. Larger bodies return 413 before any parsing or model work.
Request body — POST /decide64 KB maximum (413 beyond).
Request body — POST /decide/batch512 KB maximum, up to 100 texts per call (413 beyond).
Validation costA semantically invalid v2 body returns 422 and consumes no rate-limit budget — validation runs before the limiter.
2 — POST /decide/v2

One state, typed questions.

Send one state text — the message, ticket, transaction, or case the decision is about — plus 1–16 questions. Each question is answered independently and echoed back under its caller-chosen ID in answers. You define the vocabulary in every request: your statements, your options, your levels.

FieldContract
stateRequired string, 1–32,768 characters.
questionsRequired object, 1–16 entries. Keys are your question IDs (1–64 chars), echoed in the response.
type: "noul" (yes/no)instructions is a statement to judge true or false about the state — a hypothesis, not a question. Question form (“Is this…?”) is rejected with 422. Max 4,096 chars. The answer carries probability that the statement holds.
type: "choice"options: 2–64 entries, each an option ID mapped to a description of what the option means. Bare labels are rejected with 422 — describe every option. Optional instructions. The answer carries the winning choice and per-option probabilities.
type: "score"levels: 2–10 ordered description strings, lowest first. Optional instructions. The answer carries a numeric score on the level-index scale (see §3).
vertical (noul only)A noul question may set "vertical": "spam" to be answered by the specialised spam model instead of the general engine (§4). No other vertical exists today.

Example 1 — yes/no: is this purchase within the mandate?

request — POST /decide/v2
{
  "state": "Agent requests a $42 charge to a design tool the user already subscribes to. Mandate on file: software purchases up to $50/month are pre-approved.",
  "questions": {
    "within_mandate": {
      "type": "noul",
      "instructions": "This purchase is within the user's recorded mandate"
    }
  }
}
example response — 200
{
  "answers": {
    "within_mandate": {
      "type": "noul",
      "probability": 0.92,
      "confidence": 0.839,
      "uncertain": false,
      "escalated": false,
      "tier": 1,
      "reviewed_by": null
    }
  },
  "version": "v10",
  "request_id": "9c1f…",
  "latency_ms": 41.2
}

Read: the statement probably holds (0.92), the engine is confident, no flags — proceed.

Example 2 — multiple choice: route this ticket

request — POST /decide/v2
{
  "state": "Customer writes: charged twice for March, the app shows two identical invoices and support has not replied in three days.",
  "questions": {
    "route": {
      "type": "choice",
      "options": {
        "billing": "Payment, invoice, refund, and duplicate-charge problems",
        "technical": "App errors, crashes, login, and sync problems",
        "account": "Plan changes, profile, and account-closure requests"
      }
    }
  }
}
example response — 200
{
  "answers": {
    "route": {
      "type": "choice",
      "choice": "account",
      "probabilities": {"billing": 0.391, "technical": 0.186, "account": 0.423},
      "confidence": 0.423,
      "uncertain": true,
      "escalated": true,
      "tier": 1,
      "reviewed_by": null
    }
  },
  "version": "v10",
  "request_id": "9c1f…",
  "latency_ms": 96.7
}

Read: a close call between two queues, so the answer arrives flagged uncertain / escalated instead of silently misrouting — do not auto-act on a flagged answer (§3).

Example 3 — scored: how urgent is this case?

request — POST /decide/v2
{
  "state": "Production API returning 500s for one tenant since 09:12; two enterprise accounts affected; workaround posted.",
  "questions": {
    "urgency": {
      "type": "score",
      "levels": [
        "Routine: no user impact, handle in normal queue order",
        "Elevated: some users affected, handle today",
        "Critical: paying customers blocked, page the on-call now"
      ]
    }
  }
}
example response — 200
{
  "answers": {
    "urgency": {
      "type": "score",
      "score": 1.62,
      "probabilities": {"0": 0.08, "1": 0.22, "2": 0.70},
      "confidence": 0.70,
      "uncertain": false,
      "escalated": false,
      "tier": 1,
      "reviewed_by": null
    }
  },
  "version": "v10",
  "request_id": "9c1f…",
  "latency_ms": 88.3
}

Read: score 1.62 sits between level 1 (“Elevated”) and level 2 (“Critical”), leaning Critical — probabilities are keyed by level index, lowest first.

3 — Reading an answer

Every answer carries its confidence.

The response envelope is answers (one entry per question ID), version (the API code version, currently "v10"), request_id, and latency_ms. Every answer, of every type, carries the same core fields:

FieldMeaning
type"noul", "choice", or "score" — echoes the question type.
probability (noul)Probability that the statement holds, 0–1.
choice + probabilities (choice)The winning option ID, and the probability of every option, keyed by your option IDs.
score + probabilities (score)A numeric score on the level-index scale: 0 is your lowest level, and the value may land between levels (1.62 = between levels 1 and 2). probabilities gives the mass on each level, keyed by index as a string ("0", "1", …).
confidenceHow strongly the engine stands behind this answer, 0–1. For noul it is the distance of probability from the 0.5 boundary, rescaled; for choice, the winning option’s probability; for score, the probability mass on the nearest level.
uncertain / escalatedThe safety flags. They move together: both are true when the engine could not reach a confident verdict on its own. See the contract below.
tier1 or 2 — which stage of the engine produced the final answer. A first-pass answer under the confidence threshold is re-checked by a larger second stage where provisioned; if the answer still can’t reach confidence, the flags above are set.
reviewed_byThe engine version that produced a tier-2 answer (for example "fd1-nli-v1"; "fd1-spam-int8-v1" on the spam vertical). null when tier 1 answered alone.
vertical (spam noul only)"spam" — marks an answer produced by the spam vertical (§4).
errorPresent and true only when that one question’s engine call failed. The call still returns 200; the failed answer arrives with uncertain and escalated set. Treat it as no answer.
The escalation contract: when uncertain or escalated is true, the engine is telling you this answer is not safe to act on automatically. Do not auto-act — where the larger second stage is provisioned it has already re-checked the answer inside the cascade (see tier / reviewed_by above), and it still could not reach confidence. That flag, not the raw confidence number, is the product’s safety contract.
4 — The spam vertical

One vertical, not the product.

A noul question may carry "vertical": "spam". It is then answered by the specialised spam model — the measured spam engine behind the v1 endpoint — instead of the general decision engine. instructions is still required by the schema but the verdict is about the state as a whole: probability is P(the state is spam), and the answer carries "vertical": "spam". Spam is one vertical of FD-1; the general engine above is the product.

request — spam vertical question
{
  "state": "Congratulations! You have been selected to claim a free prize. Send your bank details now.",
  "questions": {
    "is_spam": {
      "type": "noul",
      "vertical": "spam",
      "instructions": "This message is spam"
    }
  }
}
5 — v1 endpoints (frozen)

The original spam API, unchanged.

POST /decide is the frozen v1 spam/ham endpoint, live since launch and kept unchanged for existing callers. Send one text; get one verdict. POST /decide/batch does the same for up to 100 texts per call (512 KB body cap; each text consumes one rate-limit unit). Both require the same Bearer key — except that /decide also serves the keyless demo lane from this site’s pages, under a tighter 2 KB body cap.

request — POST /decide
{"text": "Free prizes, claim now!"}
example response — 200
{
  "decision": "spam",
  "confidence": 0.98,
  "escalated": false,
  "tier": 1,
  "reviewed_by": null,
  "uncertain": false,
  "model": "v1",
  "version": "v1",
  "latency_ms": 21.4
}

New integrations should build on /decide/v2 — v1 decides spam vs. ham only, and its contract is frozen by design.

6 — Errors

Failures, in the open.

Every error body has the same shape: an error message, a machine-readable code, and the request_id. A 422 additionally carries the full errors list.

error body — 422 example
{
  "error": "questions.route.options.billing: each option needs a non-empty description (bare labels classify badly — describe what the option means)",
  "code": "UNPROCESSABLE_ENTITY",
  "request_id": "9c1f…",
  "errors": [
    {"loc": "questions.route.options.billing",
     "msg": "each option needs a non-empty description (bare labels classify badly — describe what the option means)"}
  ]
}
StatusCodeMeaning
400BAD_REQUESTThe body is not JSON, or not a JSON object (on v1: also a missing text field).
401UNAUTHORIZEDMissing or invalid API key. Authentication is answered before validation: an unauthenticated request gets 401 even if its body is also invalid.
413PAYLOAD_TOO_LARGEBody over the endpoint’s cap — 128 KB on /decide/v2, 64 KB on /decide, 512 KB on /decide/batch.
422UNPROCESSABLE_ENTITYValid JSON, semantically invalid: question-form instructions, an option without a description, more than 16 questions, a state over 32,768 chars. errors lists every problem as {loc, msg}. Costs no rate-limit budget.
429RATE_LIMITEDOver 100 requests/minute per key (v2 questions count individually). Honour the Retry-After header.
500INTERNAL_ERRORThe decision failed server-side. Safe to retry; quote the request_id if you contact us.
503SERVICE_UNAVAILABLEThe decision engine is unavailable (for example during a cold start or a deploy). The request is not at fault — retry shortly.
Cold starts: the service runs on a free tier that sleeps after ~15 idle minutes; the first request after idle can take up to ~90 s while the container boots. Warm it with an unauthenticated GET /health before latency-sensitive work.
7 — Corrections & service endpoints

When the engine gets it wrong.

File a correction with POST /review: for a v2 decision, send the question, the state, and your correct answer, using the decision response’s request_id as the decision_id (required when the correction’s source is escalation or audit). Corrections are how the loop learns — they are accepted from the key’s registered tenant.

EndpointContract
GET /healthOpen, no key. Liveness and model status — use it for uptime checks and cold-start warm-up.
GET /versionOpen, no key. Returns {"code": "v10", "model": "v1"} — code is the API contract version; model reports the v1 spam-model version, by design.
